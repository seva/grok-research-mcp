## Learnings
- `filelock` defaults to `thread_local=True`: acquire/release via `asyncio.to_thread` run on different workers, so release silently no-ops. `thread_local=False` is mandatory for the to_thread pattern.
- Patching module globals per-coroutine under `asyncio.gather` is broken: first coroutine's context-exit restores the real function, clobbering the second's patch. Patch once outside `gather`. (One stray real grok.com call escaped this way during test debugging — returned a live 429.)
- Fresh `FileLock` instance per acquisition (not a shared global): shared instance degrades to counter-based reentrancy, not real contention.
- `FileLock(...).is_locked` on a new instance reports its own state, not the file's — probe contended locks with `acquire(timeout=0)` + `Timeout`.

## Decisions
- `filelock` over named Windows mutex: cross-platform (macOS support landed upstream in Phase 6); pywin32-mutex would fragment behavior.
- Variant b (async body, lock acquire/release in threads) over variant a (whole body in `to_thread`): keeps async streaming intact.
- 429 left unretried for now; preventive protection (jitter + serialization) is the mechanism, reactive retry is #26.

## Tradeoffs
- `timeout=-1` (wait forever) on the file lock: a crashed holder relies on OS fd release; a hung grok.com response (120s httpx timeout bounds it) blocks followers. Accepted — matches "fully disable parallel execution" spec.
- Two lock layers (asyncio + file): slight redundancy, but fast path avoids file I/O for the common single-process case.

## Alternatives
- Named Windows mutex: rejected — Windows-only, upstream just invested in macOS.
- Shared timestamp/cooldown file: rejected — rate-limit approximation, not mutual exclusion; fails the spec.
